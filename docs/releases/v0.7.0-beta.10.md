# ScanStudio v0.7.0-beta.10

beta.9 reached its first real scanner on Windows today: a Windows 10 machine,
WSL2 with Ubuntu 24.04, usbipd-win, and a Nikon LS-5000 attached through the
bridge. Every layer of that stack worked -- all five setup probes green, the
real device discovered, connected, live status streaming, the hardware-session
motion latch honored end to end. The last click found the bug this release
fixes: the Preview button did nothing. This release exists so the Windows
preview path works at all; nothing else changed.

## Everything that changed

### Windows ran the app in an insecure browsing context; Preview died silently

- On Windows the app is served from an origin the embedded WebView2 runtime
  does not treat as a secure context, so two standard web APIs the app relied
  on -- the UUID generator used to correlate preview requests, and the
  clipboard writer -- simply do not exist at runtime there. The preview
  request minted its correlation id with a bare call, which threw before any
  state was recorded, and the click handler deliberately consumed rejections
  because the session store owns typed failure reporting. The result was a
  button that did nothing: no busy state, no failure banner, no wire request,
  against a connected real scanner. macOS never sees this because its webview
  origin is a secure context, and no test could see it because test
  environments provide these APIs unconditionally.
- The window now opts into the https origin scheme on Windows, restoring a
  secure context and both APIs. The content-security policy admits the https
  variants of the internal IPC and asset origins alongside the existing ones.
  No app state is origin-keyed, so nothing is lost in the scheme change.
- Defense in depth: correlation ids now come from a helper that falls back to
  a non-throwing UUID-shaped generator when the platform withholds the real
  one, and clipboard writes go through a shared helper that reports
  unavailability instead of throwing. All three copy buttons (the Windows
  setup checker's probe copy, the diagnostic report copy, and the
  frame-metadata argument copy) now show "Clipboard unavailable" when
  degraded rather than silently doing nothing, driven by a single status
  that cannot contradict itself across rapid clicks. The preview click
  handler still consumes the store's typed refusals, but a failure before
  the wire call is now recorded as a typed request failure and rendered by
  the existing failure banner -- the exact class that made this bug
  invisible.

### Preview tiles could not render on Windows either

- Adversarial review of the fix found the next wall before it shipped: on
  Windows the webview serves custom protocols through mapped local origins,
  and the three preview-tile images hardcoded the raw custom-scheme URL form
  that never reaches the app's handler there -- with a content-security
  policy that would have blocked the mapped form anyway. Tile URLs are now
  derived from the document origin so each platform gets the form its
  webview actually routes, and the policy admits the mapped origins. The
  native handler reads only the query string, so both forms hit identical
  code.
- The Windows setup checker now also reports a "Web APIs" line -- whether
  the webview considers itself a secure context and whether the UUID and
  clipboard APIs exist -- so any future regression of this class is visible
  in the checker itself.

## Validation

- Root cause was established live on the Windows machine and confirmed by an
  independent witness: the setup checker's copy button, which uses the same
  gated clipboard API bare, left the Windows clipboard empty when clicked in
  the same session where sibling buttons and the store's own state machinery
  were all demonstrably working.
- A regression test now runs the preview request path against the exact
  runtime shape live Windows exposed (a crypto object with no UUID
  generator) and asserts the request is sent with a correctly shaped
  correlation id. Restoring the old bare call makes this test fail with the
  same TypeError observed live -- the test is mutation-proven.
- Full Tauri frontend suite: 61 files, 438 passed, 6 expected skips, with
  the TypeScript build clean. New coverage includes a rendered-button
  regression that drives the real Preview control with the UUID generator
  absent, a sweep test that fails if any production source outside the
  guarded helper module touches the two gated APIs directly, and the
  clipboard-unavailable and rapid-click status semantics. All other suites are untouched by this change
  and remain as validated in beta.9; all continuous-integration jobs
  including the vendor-mirror and PyPI byte-comparison gates are green on
  the release commit.
- Both the root cause and the diff passed independent adversarial review
  before merge.

## Platform support and installation

- **macOS Apple Silicon -- Beta:** the Nikon LS-5000 real-film workflow
  remains the validated hardware path. Download
  `ScanStudio-0.7.0-beta.10-macOS-arm64.dmg`.
- **macOS Intel -- Preview:** built and package-tested natively in CI; real
  scanner validation is still pending. Download
  `ScanStudio-0.7.0-beta.10-macOS-x86_64.dmg`.
- **Windows x64 -- Preview:** use the setup executable on a clean system. The
  portable zip requires Microsoft Edge WebView2 to be installed already.
  Scanner access requires WSL2, Ubuntu 24.04, and usbipd-win.
- **Linux x64 -- Preview:** choose the AppImage or portable tarball. The host
  must provide compatible SANE/libusb runtime packages for discovery and
  scanning; the eject path does not use SANE.

The bundled CoolScanPy driver remains 0.7.2, identical to beta.9 and to the
sdist published on PyPI; the release gate byte-verifies that equality.

All macOS builds in this release are ad-hoc signed and unnotarized. The
Windows installer and Linux packages are unsigned. Download from the GitHub
Releases page, verify the package against `SHA256SUMS`, and keep the prior
installed app or DMG as a rollback artifact. On macOS, use the normal
Control-click **Open** confirmation if Gatekeeper asks; do not disable
Gatekeeper globally.

## Known limitations

- The full Windows live preview -- film loaded, frame registration
  established on real hardware -- is the next validation step on the live
  rig; today's run validated every layer up to the fixed button and stopped
  where the bug stopped it. Windows remains a preview platform until that
  completes.
- Device discovery runs at app launch only. If the WSL bridge stack becomes
  healthy after the app starts, the real scanner appears only after an app
  restart; the setup checker reports the stack green either way.
- The Windows app writes no log file; diagnosing Windows-side issues
  currently relies on the in-app setup checker and diagnostic bundle export.
- The attended-binding path has not yet been exercised on a roll that
  genuinely detects at medium confidence. The unattended thresholds are
  unchanged.
- A mounted slide cannot be ejected by command at all; the interface
  specification marks the mount adapter's unload capability absent. The
  driver refuses typed before any motion; the physical remedies remain the
  adapter's manual eject button or power-on auto-eject.
- Motion arming on Linux remains deliberately manual: both the environment
  variable and the non-empty latch file must be set by the operator.
- No Apple Team ID, Developer ID Application identity, secure signing
  timestamp, notarization, or staple is configured yet. Automatic
  installation therefore fails closed by design; this beta must be installed
  manually.
- Intel macOS, Windows, and Linux remain previews pending real-scanner
  end-to-end validation of this release's binaries.
- The separate web/gateway work is not included in these desktop release
  packages.
